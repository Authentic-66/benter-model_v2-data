# Phase 3B — Full GP Dataset Load

_Generated by `scripts/analyze_full_load.py`. Parser version: `0.1.0`._

## Headline Findings

**Parser holds at scale.** 1,480 of 1,483 PDFs (99.80%) loaded cleanly into
`gp_full.db`. The three failures are upstream PDF corruption (PDFMiner reports
`Non-Ascii85 digit found` on three specific Equibase files) — the parser
itself is not the bottleneck. The chart format is consistent across all 8
years and three filename conventions.

**14,857 races and 116,311 starters in 73 MB of SQLite.** Per-entry
completeness for the four most important signals matches the 100-PDF Phase
3A sample within ±0.5 pp, confirming no scale-dependent regressions:

| Field | Coverage 2019-2026 |
|---|---|
| `final_odds` (Benter anchor) | 100.0% |
| `trip_comment` | 100.0% |
| `pace_calls_json` | 100.0% |
| `finish_pos` | 99.4% |
| `beaten_lengths` | 86.8% (chart often omits margin for tail-end finishers) |
| `speed_figure` | 0.0% (not present in Equibase standard charts; Phase 3C) |

**Throughput.** 270 races/min from a cold start; resumable from cache makes
the second pass effectively instant. Initial wall clock 55 min; full re-runs
amortize to a few seconds.

**Coupled entries: zero observed in GP corpus.** Doug flagged this as a
schema-correctness concern; the schema and parser handle `1A`/`1B`-style
program numbers when present (`program_num` is TEXT, `post_pos` is INTEGER
representing the actual gate), but Gulfstream Park does not couple entries
in any of the 1,480 successful charts spanning 2019-2026. The architecture
remains correct for other tracks that do use coupling.

**Scratched-horse handling works as designed.** 8,825 races contain at
least one scratched horse; of those, 6,787 have program-number gaps (e.g.
`1, 2, 3, 5, 6, …` after #4 scratches). In every sample inspected, the
`post_pos` field is sequential (`1, 2, 3, 4, 5, …`) while `program_num`
preserves the printed value. Feature engineering can therefore use
`post_pos` for true gate-relative features and `program_num` for ID joins
back to chart text.

**DQ winners cleanly handled.** 219 races contain a horse whose name is
relabeled `DQ-…` in the chart. The parser uses the WPS payouts table as
ground truth: `finish_pos = 1` is the official winner, the DQ'd horse is
preserved as a separate `horses` row with its `DQ-` prefix intact, and no
DB winner is missing a win payout (`win_payout` set for every
`finish_pos = 1` row except DQs themselves).

**Dead heats handled naturally.** 190 finish-position buckets contain 2+
horses tied — multiple rows simply share the same `finish_pos`, with each
row carrying its own beaten-lengths value (typically identical for ties).

**Cancelled race days are non-fatal.** 104 races across the corpus contain
nothing but a "Cancelled-Weather" header. The parser records them as zero-
field-size races and emits a `horse_table_header_not_found` warning rather
than failing. Feature engineering can filter them via `field_size = 0`.

**New edge cases discovered at scale (vs Phase 3A 100-PDF sample):**

- **Cancelled race days** (104 races) — `field_size = 0` with no chart body.
- **`STARTERSTAKES` race-type variant** (~60 races) — the parser doesn't have
  this exact category in its known list, so the stakes name gets glued onto
  the type string (e.g. `STARTERSTAKES Old Hickory S.`). Cosmetic only;
  these races are still queryable by `race_type LIKE 'STARTERSTAKES%'`.
- **Unusual equipment codes** (~10 entries) — bare `f` (front bandages
  without Lasix) and `b` (blinkers alone). Parsed correctly when isolated
  but a handful of rows confuse the tokenizer.
- **80 horse rows** (0.07% of all entries) fail to parse cleanly — almost
  all are DNF horses whose pace calls are entirely `---`. Logged as
  `horse_row_unparsed` warnings; the rest of the race ingests normally.
- **Three corrupt PDFs** — PDFMiner cannot decode their Ascii85 streams.
  These are upstream issues (likely OCR rescan artifacts in the Equibase
  archive).

**Validation strategy.** A 50-race random spot check against the cached JSON
sidecars showed **0 discrepancies** in field_size, distance_yards, or
winner — the DB faithfully reflects what the parser extracted.
